# EasyCDR IP の 8b10b デコーダ挙動の解析手順

Gowin EasyCDR IP（暗号化）の 8b10b デコーダが「どの方式か」を実機で特定するための
手順と結果の記録。ユーザーガイド IPUG1040 には「デコードして出力、`error_o`=1 は不整合
または異常、`dout_o[9]` はほとんどの場合 0」としか書かれていないため、任意の 10 bit
符号群を送り込んで応答を観測する。

## 1. 構成

```
Tang Primer 25K (1 枚)
  自己試験 TX: easycdr_trace_tx (16bit カウンタ) --> trace_sym_inject --> OSER10 --> ELVDS_OBUF --> pmod0 L1 (G7/G8)
                                          ^ 'J' でホストから 10bit シンボル列を注入 (最大 64、ループ再生)
  USB-C ケーブル: pmod0 のモジュール <-> pmod2 のモジュール (ケーブル内で TX2<->RX2 クロス)
  RX: pmod2 L0 (G11/G10) --> EasyCDR IP (10bit + Word Align K28.5 + 8B/10B) --> trace_capture (生モード)
  ホスト: serial-bridge (UART 115200) <-- host/decoder_probe.py
```

- 送信側は本来のトレース TX と同じ `easycdr_trace_tx`（8b10b エンコーダは `rtl/displayport` の
  RD 管理付き）。注入器 `rtl/trace/trace_sym_inject.veryl` はエンコーダ出力の後段でシンボル列を差し替える。
- 受信側は通常運用と同じ IP 構成（`OUTPUT10BIT` + `WORD_ALI` + `DECODE_8B10B` + `K_28_5`）。

## 2. 追加したホストコマンド (trace_capture)

| コマンド | 内容 |
|---|---|
| `R mode` | 生キャプチャモード。1 のとき受信語をすべて `{align, err, dout[9], K, data[7:0]}` の 12 bit で記録（レコード抽出やコンマ除去をしない）。返信 `R` |
| `J mode len sym0_lo sym0_hi ...` | 注入リストのロードと開始。sym は 10 bit LE（bit 0 = 線路上で最初のビット = 8b10b の a）。mode 0 停止（コアのストリームに戻す）、1 一回再生、2 ループ。返信 `J` |
| `S` / `D` | 生モードでの即時キャプチャとダンプ（16Ki 語 = 164 µs 分、2 バイト/語: 先頭バイトが `{align, err, dout9, K}`、次がデータ） |
| `L` | リンク診断（ロック、整列、コンマ数、誤り数） |

## 3. 符号の規約

- 10 bit 符号群は `abcdei fghj` の順に線路へ出す。Python 側の `encode(x, y, rd, k)` は
  標準の 5b/6b・3b/4b 表からランニングディスパリティ（RD）を追跡して符号を作る。
  表は D0.0、K28.5、K28.1、K28.7、D17.7（A7 必須）、D3.7 などの既知符号で自己検査済み。
- 注入リストはループ再生なので、リスト全体で RD が開始値に戻るよう D3.0（6b 中立、4b ±2）を
  詰め物にして閉じる。閉じていないと 2 周目以降が RD 違反になり結果が汚れる。
- RD 違反を意図的に作るときは、対象シンボルを逆 RD 形で送り、**後続はその形が作った RD に
  合わせて**符号化する（違反が 1 シンボルに限定される）。
- 無効符号群（表に無い 10 bit 値）は実際のディスパリティで RD を進める。

## 4. 試験項目 (host/decoder_probe.py)

| # | 内容 | 見るもの |
|---|---|---|
| T0 | 注入なし（コアのストリーム）を生モードで捕捉 | 生モードの動作確認、bit 9 の出現統計 |
| T1 | D0.0〜D14.0 + K28.5、RD 正常 | 基準: 全語 err=0、復号値一致、シンボルごとの bit 9 |
| T2 | 同列で D7.0 を逆 RD 形（有効符号、RD 違反）で送る | RD 違反を検出するか、どの位置に err が立つか |
| T3 | 無効符号群 6 種（全 0、全 1、6b=000000、6b=111111、4b=0000、4b=1111）を有効 D の間に挿入 | err、そのときの dout、bit 9 |
| T4 | 12 種の K コードを RD に従った形で送る / T4b 全部 RD+ 形で送る | K フラグと値、RD 違反時の挙動 |
| T5 | D.x.7 の代替形 A7: 必須ケース、D3.7 に無理に A7、D11.7 で A7 を使わない | 代替形の受理範囲 |
| T6 | T1 のビット列を 1/3/5/9 bit 回転（コンマの位置がシンボル境界内で動く） | 再整列するか、`align_flag` の挙動 |
| T7 | D0.0〜D31.7 系 32 シンボルで bit 9 の総覧 | bit 9 がディスパリティ・RD・K のどれに相関するか |

各試験は「リストを 'J' 2 でループ再生 → 50 ms 待つ → 'L' を 2 回（カウンタクリア後の 50 ms 分）→
'S' 生キャプチャ → 'D' ダンプ」の順で、捕捉 16Ki 語をリスト周期で折り畳み、位置ごとの最頻値を表にする。

## 5. 実行

```sh
# 25K のみ、USB-C ケーブルを pmod0 <-> pmod2。serial-bridge を起動しておく
python3 host/ctrl_test.py --selftest       # 自己試験ストリームの受信確認
python3 host/decoder_probe.py              # 全試験 (--tests 1,3 で選択)
```

注意: この配線では Nano9K は繋がっていないので、`ctrl_test.py` の通常項目（逆方向チャネル）は
失敗する。受信側は自分のストリームで正常にロックするため「リンクは生きているのに制御が効かない」
ように見える。

## 6. 結果

### 6.1 実行環境

2026-09-13、25K 単体（pmod0↔pmod2 ループバック）、IDE 1.9.12 の EasyCDR IP v1.4（`easycdr_1912`、
`OUTPUT10BIT` + `WORD_ALI` + `DECODE_8B10B` + `K_28_5`、DELAY 0/21）、1 Gbps。
各試験は捕捉 16384 語（リスト周期で折り畳んで位置ごとに集計。表の count/total が全一致 = 挙動が決定的）。

### 6.2 判明したこと

| 項目 | 結果 |
|---|---|
| ランニングディスパリティ (RD) の検査 | **する**。D0.1 を逆 RD 形（有効符号、RD 違反）で送るとその語だけ `error_o`=1、復号値は正しい (T2) |
| RD 不一致時の内部状態 | 受信した形に **RD を合わせ直す**。両形とも中立な D7.1 を逆形で送ると、その語と、次に RD 依存の形を持つ語（正しい形で送った D7.1）の 2 語が誤りになる = 逆形を受けた時点で内部 RD を反転している (T2 対照) |
| 無効符号群 | `error_o`=1、データは表引きの残骸を出す: 全 0 → K=1 0xff、全 1 → K=1 0x14、6b=000000 → K=1 0x1f、6b=111111 → K=1 0x14、4b=0000 → D 0xe0、4b=1111 → D 0x00。4b=0000 の場合は直前の有効語 (D4.1) にも誤りが立った (T3) |
| 誤り時のデータ出力 | 抑止しない（上記の値がそのまま `dout_o` に出る） |
| K コード 12 種 | K28.0〜K28.7、K23.7、K27.7、K29.7、K30.7 すべて K=1 で正しく復号 (T4) |
| K コードの逆 RD 形 | 復号値は全部正しい。`error_o` は K28.0/2/3/4/6/7、K29.7 で 1、K28.1/K28.5/K23.7/K27.7/K30.7 で 0（RD の合わせ直しの結果として説明できる範囲、詳細未整理） (T4b) |
| D.x.7 の代替形 A7 | 必須の場面 (D17.7/D20.7 RD−、D11.7 RD+) は誤りなし。**非必須の場面で A7 を使うと誤り扱い**（値は .7 として正しく復号）。必須の場面で基本形を使っても誤りにならない (T5) |
| `dout_o[9]` | 全試験・全語（無効符号、非整列の雑音を含む約 40 万語）で **常に 0**。ディスパリティや誤りの表示ではない。用途不明（予約と考えるのが妥当） |
| ワード整列の再整列 | **整列後はシンボル位相が変わっても再整列しない**。入力ビット列を 1〜9 bit 回転させると、5 bit のときだけ即座に復帰し、それ以外は 3 秒待っても `align_flag_o`=1 のまま復号誤りが出続ける (T6、回転 0〜9 の全掃引) |
| 整列の解除条件 | 復号誤りでは解除されない。線路が無遷移（全 0 シンボル）になると `align_flag_o` が 0 になり、信号が戻ると再整列する |
| 復号誤りの位置 | `error_o` は該当語と同じ語位置で立つ (T3 の 4b=0000 だけ直前の語にも立つ) |

### 6.3 解釈

- デコーダは **RD 追跡型**で、符号表の照合に加えて「今の RD で期待される形か」を検査し、違反時は誤りを立てつつ受信形に RD を同期し直す。
  受信側だけで運転できる保守的な設計で、送信側の RD 初期値には依存しない（初回の不一致が 1 回誤りになるだけ）。
- 誤りは 1 本の `error_o` にまとめられ、符号違反と RD 違反は区別できない。誤り時もデータは出るので、上位でレコードを捨てる判断には `error_o` を見る必要がある。
- 整列は「取得後は固定」で、位相ずれからの自律回復は 5 bit の場合しか起きない（内部の 5 bit 単位の処理に由来すると推測）。
  トレースリンクでは送信側のソフトリセットが OSER10 を触らずシンボル境界も保つため実害はないが、
  **送信側で bit スリップが起きるとリンクが固まる**。25K のコンマ監視 (`act_ok`) と 'L' 診断で検出し、IP リセット（ボードのリセット）で復旧する運用になる。
- `dout_o[9]` は TMDS のような DC バランス表示ではなかった（少なくとも 1 Gbps 8b10b 構成では不変）。

### 6.4 未解決

- T4b の K コード逆形で `error_o` が立つ／立たない条件の厳密な整理（RD 合わせ直しモデルで再現できるか）
- T3 で無効 4b=0000 の直前の語に誤りが立つ理由（ラン長検査の可能性）
- 16 bit 生モード構成での `dout_o[9]`（未試験）
