# Gowin EasyCDR の原理と実機で確かめたこと

Tang Primer 25K（GW5A-25）上の EasyCDR IP、および同じ仕組みで自作した受信器（`rtl/oscdr`）
について、動作原理・関連する符号化・実機解析の結果をまとめる。詳細な手順や生データは
各節で示す文書・作業ログを参照。

対象の一次資料:
- IPUG1040-1.4E Gowin EasyCDR IP User Guide — https://www.gowinsemi.com/upload/database_doc/2687/document/69ebd0bcda780.pdf
- UG304-1.3.8E Arora V Programmable IO (GPIO) User Guide（OSIDES32 §4.2.13、IODELAY §4.4.1）— https://cdn.gowinsemi.com.cn/UG304E.pdf
- EasyCDR Reference Design（zip）— https://www.gowinsemi.com/upload/database_doc/2674/document/6683b7c253ea7.zip
- IDE 同梱シミュレーションモデル `IDE/simlib/gw5a/prim_sim.v`（IODELAY / OSIDES32 / PLLA の振る舞い記述）

## 1. 方式: ブラインド・オーバーサンプリング

### 1.1 PLL 型 CDR との違い

| 観点 | PLL 型（専用 SerDes） | ブラインド・オーバーサンプリング型（EasyCDR） |
|---|---|---|
| 受信クロック | 位相比較器と PLL / 位相補間器でデータに同期させる | 自分の水晶から作った固定周波数・固定位相のまま（送信側と無関係） |
| サンプル | 1 UI に 1 回、常にアイ中央 | 1 UI に 4 回、後段ロジックが「どのサンプルを使うか」を選ぶ |
| 周波数差 | クロックがデータに一致する | 判定点を 1 サンプル (1/4 UI) ずつずらして追従し、1 UI ずれたら 1 語のビット数を 7 / 9 にして吸収（プレシオクロナス、±5000 ppm @1 Gbps） |
| 復元クロック | 外部に出せる（再送出や同期系に使える） | 作らない。`share_clk` は受信側 PLL 由来の固定クロック |
| 時間分解能 | 1/32〜1/64 UI | 1/4 UI |
| 必要な回路 | トランシーバ | GPIO + PLLA + IODELAY + OSIDES32 |

「クロック信号を復元していない」という意味では狭義の CDR ではなく、論文では
*blind oversampling CDR* / *oversampling data recovery* / *phase-picking CDR* と呼ばれる
（古典: Yang, Farjad-Rad, Horowitz, "data recovery using oversampling", 1998）。
機能的には「付随クロックなしのビット列から判定時刻とビット境界を復元する」ので、
業界では CDR の一種として扱われる。定訳はなく「オーバーサンプリング型 CDR」で通じる。

### 1.2 判定点の選び方（EasyCDR 相当の自前実装 `rtl/oscdr` で確認した動作）

1. 32 サンプル語の隣接サンプル間で XOR を取り、遷移が現れた位置を 4 クラス（UI 内の位置 0〜3）ごとに数える。
2. IIR で平滑化し、遷移から最も遠いクラス（コスト最小）をデータ判定点に選ぶ。
3. 周波数差で遷移位置が流れると判定点を ±1 クラス動かし、1 UI 分回ったら語のビット数を 7 / 9 にする（ギアボックス）。
4. 遷移が来なければ統計が更新できない → 遷移密度（8b10b、PRBS、スクランブル）が前提。

## 2. OSIDES32: 4 サンプル/UI を作る仕組み

UG304 §4.2.13 と `prim_sim.v` の OSIDES32 モデルから読み取れる構造:

```
IBUF ─┬─ IOL A: IODELAY_0 (静的 0 段)      ─→ 4 相サンプラ (P/QP/N/QN 各 1 FF, 立上り) ─→ 16 サンプル ┐
      └─ IOL B: IODELAY_1 (静的 21 段≈UI/4) ─→ 4 相サンプラ                              ─→ 16 サンプル ┴→ 交互に並べて Q[31:0]
       FCLK: 4 相 500 MHz (PLLA CLKOUT0..3、PE_COARSE/FINE で 0/90/180/270°)、PCLK = FCLK/4 = 125 MHz
```

- 4 相の**単エッジ**でサンプルする（DDR ではない）。1 FCLK 周期に 4 サンプル = 1 UI に 2 サンプル。
- これだけでは足りないので、差動ペアの相方ピンの IOL にある IODELAY_1 で UI/4 遅らせた 2 経路目を同じ 4 相で取り、
  合計 4 サンプル/UI にする。UG304 の「2 つの IOL を使う」はこれ。
- IODELAY は 256 段、1 段 ≈ 12.5 ps。1 Gbps では DELAY_1 = 21 段 ≈ 262 ps ≈ UI/4。GUI ライブラリの式は
  `DELAY_1 = floor(20/R) + 1`（R = Gbps）。742.5 Mbps 変種では 28 に設定して実機 OK。
- 1 Gbps 超（OSIDES64）: HCLK = レート/4 になって 1 経路 1 サンプル/UI に落ちるため、隣接ペアの IOL も借りて
  4 経路（DELAY_2/3 = 2UI/4, 3UI/4）にする。IPUG1040 の「隣の GPIO が使えなくなる」制約の由来。
- Q の群内順（モデル）: (遅延側, 非遅延側) のペア × P/QP/N/QN。ペア (2m, 2m+1) が「同じ FCLK エッジで取った
  遅延あり／なし」の組。

### 2.1 実機で確定した制約（公式資料に記載なし）

| 事項 | 結果 | 根拠 |
|---|---|---|
| IODELAY の動的／適応モード | **使えない**。`DYN_DLY_EN`/`ADAPT_EN` を TRUE にした時点で静的値も消え、SDTAP/VALUE/DLYSTEP をどう操作しても遅延ゼロ相当 | ペア一致率（§2.2）が 1.000 のまま。片側／両側／適応、DLYSTEP を値／段数どちらに解釈しても、名目 840 段まで不変。合成ネットリストには設定が通っている（`eda/easycdr_bert/host/dlyscan.py`、作業ログ 4.19/4.20） |
| 運転中の FCLK 位相変更（受信 PLL の DPS） | **不可**。OSIDES32 内部の FCLK→PCLK 同期が壊れ、リセットまで復旧しない | 作業ログ 4.8 |
| D 入力 | IBUF 直結が必要（UG304 も明記） | |
| 100 Ω 終端と CTLE | 上辺（IOT）ピンのみ | pins.cst のコメント |
| 静的 4× の実在 | DYN=FALSE の静的設定でのみ 4 サンプル/UI（ペア一致率 0.92）。初回は DYN=TRUE で作っていたため 2 サンプル/UI に見えていた | 作業ログ 4.8 |

シミュレーションモデルは動的ロード（SDTAP=0 で DLYSTEP を絶対値ロード、適応は DI の立下り 22 回毎に 1 段）を
実装しているので、モデルと実機は食い違う。IP が遅延を「自動生成・変更不可」の静的固定にしているのはこの制約と整合する。
追試（作業ログ 4.21）で切り分け済み: ロード後に OSIDES32 をリセットしても変わらず（手順の問題ではない）、
**単体の IODELAY を動的モードで使うと正常に動く**（SDTAP=0 で DLYSTEP を絶対値ロード、実測 1 段 ≈ 12.8 ps、
`eda/easycdr_bert/host/iodly_test.py`）。したがって IODELAY もツールも正常で、OSIDES32 に内蔵された IODELAY を
動的モードにした場合だけ効かない。OSIDES32 モードでは IOL 内の動的制御が使えない（資源共有かビットストリーム生成の非対応）と
考えるのが妥当。派生として、単体 IODELAY + IDES8 なら受信側 12.5 ps 刻みの位相掃引が組める（同期ループバック向け、未実装）。
測定の注意: DPS で位相を掃引する間、CLKDIV の出力位相は飛ぶ（分周器が再同期する）ので、音源は分周器を通さず作ること。

### 2.2 ペア一致率（遅延の実在を測る指標）

32 サンプル語のペア (2m, 2m+1) の値が一致する割合。遅延が無ければ同じ瞬間のサンプルなので 1.000、
UI/4 ずれていれば PRBS で約 12% のペアに遷移が挟まり 0.9 前後。PLL 位相や CDR の追従に依存しない
（同じクロックエッジで取る 2 サンプルの時間差だけで決まる）ので、遅延設定の検証に使える。

## 3. アイスキャン

- 本設計: 受信 CDR の判定点を凍結し、**送信側** PLLA の動的位相シフト（1 パルス = VCO/8 = 125 ps）でデータ全体を
  ずらしながら PRBS 誤りを数える。時間軸のみ、分解能 1/8 UI、開口 0.4〜0.5 UI @1 Gbps。
- AMD IBERT: 受信側のオフセットサンプラ（位相補間器 + 電圧 DAC）でデータ経路を乱さず 2 次元の統計アイを取る。
  送信側の協力不要、実データで可。
- GW5A-25 で受信側の細粒度スキャンができない理由は §2.1（動的 IODELAY 不可、受信 PLL の DPS 不可）。

## 4. 線路符号: 8b10b

### 4.1 基本

- 8 bit を 5b/6b + 3b/4b の表で 10 bit にする（abcdei fghj、a が先に送出）。IBM（Widmer/Franaszek 1983）が発明し、
  Fibre Channel、IEEE 802.3 Clause 36、PCIe 1/2、SATA、USB 3.0、DisplayPort 等が同じ表を使う。
- 目的: 遷移の保証（CDR が動く）、DC バランス（AC 結合で使える）、制御記号（K コード 12 種）。
- **ランニングディスパリティ（RD、走行/累積ディスパリティ）**: これまでの 1/0 の偏りを示す 1 bit の状態。
  各符号は RD− 用と RD+ 用の 2 形（中立な符号は同形）を持ち、送信側は偏りを打ち消す形を選ぶ。
  6 bit 部と 4 bit 部で別々に選び、偏った部分ごとに RD を反転する。D.x.7 は x = 17/18/20 (RD−) と
  11/13/14 (RD+) で代替形 A7 が必須。
- コンマ（0011111 / 1100000）は K28.1/5/7 にしか現れず、K28.5 で語境界を決める。

### 4.2 EasyCDR IP の 8b10b デコーダ（実機解析、詳細は `decoder_probe.md`）

| 項目 | 結果 |
|---|---|
| RD 検査 | する。逆 RD 形（有効符号）でその語だけ `error_o`=1、値は正しい。違反時は受信形に RD を同期し直す |
| 無効符号 | `error_o`=1、データは抑止せず表引きの残骸を出す |
| K コード | 12 種すべて復号 |
| A7 | 必須の場面のみ正常。非必須で使うと誤り扱い（値は正しい）。必須の場面で基本形を使っても誤りにならない |
| `dout_o[9]` | 常に 0（約 40 万語）。TMDS のような DC バランス表示ではない |
| 再整列 | 整列後に位相がずれても再整列しない（5 bit のみ復帰）。無遷移で `align_flag_o` が落ち、復帰後に再整列 |

送信側（`rtl/displayport/src/encoder_8b10b.sv`）は RD 管理と A7 を実装した規格準拠のエンコーダで、
すべてのシンボルを 1 インスタンスに通すため RD が途切れない。実機で復号誤り 0 を長時間維持。

## 5. 試験用データ列: PRBS

- PRBS（擬似ランダム 2 値系列）は LFSR（線形帰還シフトレジスタ）が出す最長系列（M 系列）。
  原始多項式なら周期 2ⁿ − 1、全 0 状態は不動点なので初期値は 0 以外（検査器の全ゼロ偽ロック対策が要る）。
- タップ位置 = 多項式の項 = XOR に入れる段。ITU-T O.150: PRBS7 x⁷+x⁶+1、PRBS9 x⁹+x⁵+1、PRBS15 x¹⁵+x¹⁴+1、
  PRBS23 x²³+x¹⁸+1、PRBS31 x³¹+x²⁸+1（いずれも 2 タップ）。
- 性質: ほぼ半々の 1/0、最大ラン長 n、長さ k のランは 2^−k の割合 → CDR/イコライザを実データより少し厳しく試験できる。
  受信側は自己同期（n bit 詰めて同期後に自走比較）で誤りを数える（BERT）。
- 公式リファレンス設計は PRBS を符号化なしで流し、遷移密度と DC バランスを PRBS の統計に頼る。本設計は
  実データを流すため 8b10b で保証する。
