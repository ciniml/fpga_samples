# TcpEngine — 現行設計の記録とベンチマーク (改良版比較用ベースライン)

`rtl/nvme/tcp_engine.veryl`。NVMe/TCP ターゲット用に書いた軽量 TCP サーバ
エンジン。将来ほかの用途にも使えるよう、構成・利点・欠点・実測速度を
ここに固定しておき、改良版と比較できるようにする。

計測日 2026-09-06 / Tang Nano 9K Pmod + LAN8720 / 100BASE-TX 直結 /
50MHz RMII ドメイン / ネームスペースは内蔵 PSRAM (54MHz, 512B ライン
キャッシュ)。改良版も**同一条件**で測ること。

## 構成

2 コネクション固定 (NVMe/TCP は 1 キュー = 1 コネクション: admin + I/O)。
`LOCAL_PORT` へのパッシブオープンのみ。全体が RMII の 50MHz 単一ドメイン。

### 受信 (RX)

- MAC からの 1 バイト/サイクル AXIS を `rx_pos` 駆動のパーサで解析
  (Ethernet/IPv4/TCP ヘッダをオフセット固定で拾う)。
- **インオーダのみ**: `seq == rcv_nxt` の payload だけ受理し、それ以外は
  破棄して重複 ACK を返す。再組み立てはしない。
- payload は 2KiB の RX FIFO へ。**FIFO の空き = 広告ウィンドウ**なので
  ピアがオーバランできない。アプリが吸い出したらウィンドウ更新 ACK。
- コミットは 2 段パイプライン (`cm_*` → `cm2_*`): tlast でフレームを
  ラッチ → シーケンス演算を前計算 → 状態適用。FCS が良のフレームのみ
  コミット (RX 側は TCP チェックサム検証を省略、MAC の FCS を信頼)。

### 送信 (TX)

- アプリのバイトは 2KiB のリングへ。**このリングが Go-back-N の再送
  バッファ (`snd_una..wr_seq`) を兼ねる**。
- セグメントは **1024 バイトで分割**、またはアプリのストリームが
  ~10µs アイドルしたらフラッシュ (`idle_cnt >= 512` サイクル)。
- フレーム生成は 1 バイト源関数への 2 パス: パス 1 で IPv4/TCP
  チェックサム積算 (擬似ヘッダ込み)、パス 2 でバイト出力 (60 バイト
  最小長へパディング)。SYN-ACK は MSS=1460 オプション付き。
- 再送: RTO (25M サイクル = 0.5s) で `snd_nxt` を `snd_una` に戻す
  (Go-back-N)。ファストリトランスミットなし。

### コネクション

`Closed → SynRcvd → Estab → LastAck`。インオーダ FIN で ACK し
`conn_active` を落とし (NVMe/TCP パーサをリセット)、リング枯渇後に自分の
FIN を送って最終 ACK で Closed。RST は即 Closed。

## 利点

- **小さい**: TcpEngine 単体で約 2,000 LUT / 900 ALU / 1,600 FF、BRAM は
  RX FIFO + TX リング (2KiB×2×2 = 4 BSRAM 相当)。9K に 2 コネクション分
  が収まる。
- **単一クロック**・バックプレッシャ少なめで組み込みやすい。
- RX チェックサム省略 (MAC FCS 前提) で軽い。
- ARP/ICMP は別モジュール (`eth_ip.veryl`)、TX 多重化は `eth_tx_mux.veryl`
  と分離。アプリ側は 16 ビット (2 レーン) の valid/ready バイトストリーム
  だけ見ればよい。

## 欠点 (改良版で潰したい点)

1. **インフライト上限 2KiB** — リングが再送バッファ兼用で 2KiB 固定。
   ピアの広告ウィンドウを見ずに「最大 2KiB しか飛ばさない」。これが
   ストップ・アンド・ゴーを生み、スループットの主因。
2. **ピアウィンドウ非追跡** — 相手の rwnd を無視 (小さいので実害は出て
   いないが、正しくない)。
3. **セグメント 1024B 固定** — MSS (1460) 未満。フレーム数が増える。
4. **フラッシュタイマ依存** — 1024B に満たないデータは ~10µs 待って
   から送るため、レイテンシに下駄。
5. **Go-back-N のみ** — ロス時に snd_una から全再送。ファスト
   リトランスミット/SACK なし。RTO も 0.5s と粗い。
6. **インオーダ RX のみ** — 順序が乱れると破棄 + dup ACK。
7. **1 コマンド = 1 往復に近い**直列性 (QD を上げても伸びない)。

## 実測ベースライン (改良版と比較する数値)

`spdk_nvme_perf`、-t 6〜10 秒、PSRAM ネームスペース。

### ランダム (レイテンシ寄り)

| 条件 | IOPS | MiB/s | 平均レイテンシ |
|---|---|---|---|
| 4KiB randread QD1 | 330 | 1.29 | 3.03 ms |
| 4KiB randread QD4 | 469 | 1.83 | 8.54 ms |
| 4KiB randwrite QD4 | 305 | 1.19 | 13.1 ms |
| 512B randread QD4 | 2636 | 1.29 | 1.52 ms |

### シーケンシャル (スループット寄り) ← 改良の主戦場

| 条件 | IOPS | MiB/s | 平均レイテンシ |
|---|---|---|---|
| 4KiB read QD1 | 332 | 1.30 | 3.01 ms |
| 4KiB read QD8 | 484 | 1.89 | 16.5 ms |
| 32KiB read QD4 | 62 | 1.95 | 64.7 ms |
| 128KiB read QD1 | 14.5 | 1.81 | 69.3 ms |
| 128KiB read QD4 | 16.2 | 2.02 | 254 ms |
| 128KiB write QD1 | 10.5 | 1.31 | 96.2 ms |

**要点**: ブロックサイズや QD を上げても **約 2 MiB/s で頭打ち**。
100BASE-TX の実効 (~11.8 MiB/s) の **約 16%** しか使えていない。
上限はインフライト 2KiB の窓 (欠点 1)。RTT ~1ms 相当ごとに 2KiB しか
送れない = 約 2 MiB/s、と整合する。

参考: BRAM ネームスペース版 (PSRAM レイテンシ無し) の 4KiB randrw QD4 は
999.8 IOPS だったが、これも ~4 MiB/s 級で頭打ち傾向は同じ。

## 改良版の目標

- ピアの広告ウィンドウを追跡し、**インフライトを rwnd (数十 KiB) まで**
  引き上げてストップ・アンド・ゴーを解消 (最優先)。
- MSS (1460B) セグメント化。
- フラッシュタイマ依存を減らし、送れるものは即送る。
- できれば RTO の適正化 / 重複 ACK ベースのファストリトランスミット。
- 目標スループット: 100BASE-TX の **> 70% (> 8 MiB/s)**。
- 安定性最優先: マルチキュー + 連続再接続で smoke/SPDK が安定して通る
  こと (前回の試作はここで不安定化して revert した)。

検証は `rtl/nvme/sim` の根なしフルチェーンシム (`eth_tap_bridge` の
`unix:<path>` 転送 + `sim_host.py`) と実機の両方で行う。

## 改良版 第1段: インフライト窓の拡大 (2026-09-06)

最小・低リスクの変更で頭打ちの主因 (欠点 1) を緩和:

- TX リング (再送バッファ兼用) を 2KiB → **8KiB/コネクション**に拡大。
  ホスト向けリード (c2h) のインフライトが 4 倍。
- RX FIFO (= 受信ウィンドウ) も 2KiB → **8KiB**。ホストからのライト
  (h2c) のインフライトが 4 倍。
- セグメントを 1024B → **MSS 1460B**。
- タイミング用に受信シーケンス加算の `rcv_nxt` を前段でレジスタ化
  (`cm_rcv`)。制御フローは変えていないので安定性は維持。

実機結果 (同一条件、smoke 3/3・SPDK 安定):

| 条件 | 改良前 | 改良後 | 倍率 |
|---|---|---|---|
| 128KiB read QD1 | 1.81 MiB/s | 3.55 MiB/s | 2.0x |
| 128KiB read QD4 | 2.02 MiB/s | 3.90 MiB/s | 1.9x |
| 128KiB write QD1 | 1.31 MiB/s | 1.96 MiB/s | 1.5x |
| 128KiB write QD4 | ~1.3 MiB/s | 2.03 MiB/s | 1.6x |
| 4KiB randread QD4 | 469 IOPS | 640 IOPS | 1.4x |
| 4KiB randrw QD4 | 361 IOPS | 510 IOPS | 1.4x |

リソース: Logic 84%、BSRAM **81% (21/26)**、Fmax 50.8MHz。

**残る頭打ちと次段**: リード ~3.9 MiB/s (100BASE-TX の ~33%) で再び頭打ち。
8KiB のインフライトでも 1 RTT あたり 8KiB しか送れず、ACK/ウィンドウ更新の
往復と (小さい転送では) フラッシュタイマ待ちが律速。さらに伸ばすには
(a) ピアの広告ウィンドウを追跡してインフライトを rwnd (数十 KiB) まで
上げる、(b) ACK 折り返しの短縮、(c) フラッシュタイマ依存の除去、が必要。
ただし 9K は BSRAM 81% で**これ以上バッファを増やせない** — 8KiB 超の
インフライトには Primer 20K などより大きい FPGA か、再送バッファを PSRAM に
逃がす設計が要る。第1段は「9K に収まる範囲で 2 倍」が到達点。
